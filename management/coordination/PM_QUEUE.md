## Regola di chiusura

Alla conclusione di ogni progetto o implementazione, il PM consegna sempre:

- un **Final Result interno**: cosa è cambiato, verifiche, regressioni note, stato di rilascio e prossimo gate;
- una **nota pubblica** pronta per sito e Discord, diretta e leggibile in pochi minuti.

La nota pubblica si prepara solo su funzionalità effettivamente rilasciate o dichiaratamente in prova; non include database, RPC, credenziali, vulnerabilità, dati di test o dettagli interni. Il modello stabile è in `FINAL_RESULT_TEMPLATE.md`.

**Motore Scontri V1:** il Final Result viene emesso automaticamente dal PM alla chiusura del release gate, prima di aprire V2 o nuovi miglioramenti. Il gate include verifica live, regolamento pubblicato, narratore se incluso nel rilascio e QA finale approvata.

**Sorgente di rilascio — vincolo operativo:** prima di proporre, allegare o descrivere un candidato, Claude lo scrive direttamente nella cartella finale del progetto, normalmente `sito_live/`. Non consegna candidati in Downloads, allegati, file ponte o percorsi temporanei e non chiede ad Antonello di copiare o sovrascrivere file a mano. Il handoff indica percorso assoluto, data/ora, dimensione e SHA-256 della copia appena scritta; Antonello carica solo quella copia.

**Destinazioni per tipo:** file HTML pubblicabili in `C:\theuntoldstory\sito_live\`; sorgenti Edge, SQL candidati e rollback in `C:\theuntoldstory\claude\`. Una sorgente Edge non va in `sito_live\`, per evitare che venga inclusa per errore nel materiale destinato a GitHub.

**Riconciliazione obbligatoria di una pagina:** prima di patchare un HTML, `sito_live\<pagina>` deve essere verificato contro la copia realmente pubblicata. Se l'ambiente non può leggere GitHub, Claude non ricostruisce la base da rollback né applica una patch “generica”: Antonello allega soltanto il file vivo scaricato da GitHub e Claude lo scrive, verifica e aggiorna nella cartella del progetto. Antonello non sovrascrive mai la sorgente a mano.
